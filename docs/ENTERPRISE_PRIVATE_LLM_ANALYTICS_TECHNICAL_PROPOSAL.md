# 【管理层一页摘要】（3～5 分钟速读）

### 1. 业务痛点：为什么要做这个系统？
随着公司全面引入 **OpenAI**、**Kimi**、**DeepSeek** 等大模型，管理层迫切需要掌握真实使用情况：各部门使用率有多高？主要用于技术开发、文档撰写还是数据分析？模型调用成功率如何？值得继续向哪家模型采购？
同时，公司在与供应商联合优化模型时，需要反馈使用数据。但**直接导出内部日志存在重大安全隐患**：极易暴露员工个人行为、敏感业务代码或业务结构；重度用户的调用量容易主导统计偏差；一旦多方供应商数据对比外泄，还会引发商业合规风险。

### 2. 核心价值：这个系统做什么？
**Private LLM Analytics** 是专为企业打造的**中心化差分隐私（Differential Privacy, DP）分析系统**。
一句话概括系统目标：
> **在数学级证明“绝不泄露任何单名员工使用轨迹”的前提下，让公司安全、合规地掌握宏观 AI 使用趋势，并能够向外部安全共享统计报表。**

### 3. 系统怎么做到“既安全又准确”？
系统对企业日志执行四步标准化治理：
1. **聚合到员工**：将原始明文调用流水转变为按员工归纳的宏观行为向量（严禁导出 Prompt 正文）；
2. **贡献限制（Clipping）**：约束单个重度员工对大盘的无限主导影响，防范“一个人带偏整体趋势”；
3. **注入严谨差分隐私噪声**：依据数学证明加入受控高斯扰动，从根本上防止外部反推个人身份；
4. **全生命周期隐私账本（Lifetime Ledger）**：永久记录历史发布累加的隐私消耗，绝不因重启清零，彻底防范“通过多次重复查询平均掉噪声”的攻击。

### 4. 当前系统成熟度与实际效果
- **五大业务统计就绪**：成功率、员工使用率、使用结构占比、总交互量、热门任务 Top-K。
- **真实生产准确性表现**：
  - **成功率 / 使用率 / 结构占比**：DP 发布值与内部真实统计误差仅 **0.01% ～ 0.1%**，完全满足业务决策与供应商对账。
  - **交互总量**：当前存在约 **38%** 的偏差。系统内部误差分析表明：**99.9% 的偏差来源于为保护重度用户而设置的裁剪参数（$C=20$），而非 DP 随机噪声**。下一阶段核心工作即为优化裁剪自适应算法。
- **合规审计基准**：全自动化测试套件 **542 项测试全部通过（0 失败）**，通过形式化 RDP 记账与并发防围栏安全审计。

# 第1章：为什么要建设这个系统

在企业数字化转型中，大语言模型（LLM）已迅速渗透进日常办公、技术研发与客户服务。当前公司同时采购并接入了多家主流模型：
- **OpenAI**（主力代码生成、复杂技术推理）
- **Kimi**（长文本处理、多语言文档润色）
- **DeepSeek**（数据分析、业务建模与低成本高并发任务）

### 1.1 内部管理面临的真实诉求
面对每月不断增长的模型调用成本与企业知识资产投入，公司各管理团队亟需明确以下业务问题：
1. **真实渗透率**：全公司 50,000 名员工中，到底有多少人真正把大模型用进了日常工作？还是仅有少数技术极客在重度使用？
2. **任务分布结构**：各部门在哪些场景使用 AI？是主要写代码、写文档还是做财务分析？
3. **模型效能对账**：不同模型在各专业任务上的调用成功率与稳定度如何？哪家供应商的服务值得在下个财年继续续费或扩容？
4. **任务热点演进**：最近一个月最热门的 AI 需求是什么？是否有新兴的业务痛点正在涌现？

### 1.2 外部反馈面临的数据安全红线
为了促使供应商持续改进服务质量、提供更优惠的企业定制价格，公司经常需要向供应商反馈宏观使用统计。例如：
- “过去一个月，贵方模型在技术类任务上的成功率约为 85.0%。”
- “文档类任务在本月的交互量环比增长了 20%。”

然而，传统做法如果直接提供内部明细报表或精确聚合值，将面临极高的安全与合规风险：
- **暴露员工个人隐私**：某些细分任务（如海外合规法务分析）全公司可能只有 1～2 名员工负责。一旦发布精确调用次数，极易反推特定个人的工作节奏与加班情况。
- **暴露部门组织机密**：精确的调用量变化可能提前泄露公司正在研发的新产品线或重大战略转型。
- **供应商多方信息刺探**：如果外部供应商通过反复查询或联合对比，推测出公司在其他竞争对手模型上的精确消耗份额，将在采购谈判中使公司处于不利地位。

### 1.3 核心目标
因此，建设本系统的根本目标是：
> **在不直接暴露员工个人使用数据的前提下，让公司仍然能够分析和对外分享有价值的大模型使用统计。**

# 第2章：这个系统到底做什么

**Private LLM Analytics** 在企业底层日志库与外部/内部报表消费端之间，架起了一道兼具“数学安全性”与“业务可用性”的安全防线。

系统的数据处理核心流水线如下：

```text
       企业大模型使用日志 (原始明文流水)
                      ↓
       整理成用户级统计 (按员工聚合，不保留 Prompt)
                      ↓
       限制单个员工对结果的影响 (Contribution Bounding)
                      ↓
       加入差分隐私保护 (Statistic-Specific DP Mechanism)
                      ↓
       生成可以查看和下载的统计结果 (Web 控制台 / CSV / JSON)
```

系统围绕企业决策最关心的核心指标，支持回答五类核心业务问题：
1. **覆盖度问题**：全员使用率（User Prevalence）
2. **结构分布问题**：典型员工精力分配占比（User-Normalized Share）
3. **业务规模问题**：总调用规模与容量（Interaction Volume）
4. **服务质量问题**：任务完成成功率（Success Rate）
5. **热门发现问题**：长尾需求发现（Top-K Tasks）

# 第3章：系统目前可以统计哪些数据

本系统拒绝直接套用通用的“黑盒加噪”算法，而是为每一种企业业务统计问题量身定制最契合的差分隐私处理机制。

### 1. 有多少员工在使用？（用户使用率 / User Prevalence）
- **业务场景**：全公司 50,000 名员工中，有多少比例的人在过去 30 天使用过技术类 AI？
- **业务输出示例**：`OpenAI × technical: DP 估计使用率 = 36.8%`
- **业务意义**：这个 36.8% 不是拿内部精确打卡人数直接除出来的，而是对“每位员工是否使用”进行二值化转换、加入数学可信高斯噪声后除以固定的公开员工基准（50,000 人）得到的估计值。即使某位员工突然离职或停用，最终统计结果的波动也不会超过数学隐私界限。

### 2. 员工主要拿 AI 做什么？（使用结构占比 / User-Normalized Share）
- **业务场景**：一个典型员工的精力如何分配在不同任务上？
- **业务输出示例**：`技术类 60.0% | 文档类 30.0% | 分析类 10.0%`
- **业务意义**：如果公司有一位极客员工一天调用 5,000 次技术代码，而普通财务员工一天只调用 10 次报表，传统统计会被极客严重带偏。本系统先将每个员工自身的各项任务折算为百分比（每人总权重严格等于 1.0），再综合全员平均值。这确保了展现的是“广大员工的典型工作习惯”，而非少数重度用户的个人行为。

### 3. 一共使用了多少次？（交互量 / Interaction Volume）
- **业务场景**：过去 30 天，各模型各任务单元累计消耗了多少次大模型调用？
- **业务输出示例**：`OpenAI × technical: 374,120 次交互`
- **业务意义**：统计总调用规模。由于真实世界中调用量差异极大，系统会设定一个“单人最高计入上限”（当前配置为 $C=20$），超出部分进行等比比例收缩，再添加差分隐私噪声。该统计是目前系统中最受“贡献限制参数”影响的指标。

### 4. 模型完成任务的效果怎么样？（任务成功率 / Success Rate）
- **业务场景**：大模型调用到底稳定不稳定？失败率高不高？
- **业务输出示例**：`OpenAI × technical: 成功率 = 85.08%（真实统计 84.99%）`
- **业务意义**：系统同时保护“成功交互数”与“总交互数”，使用等比因子同步裁剪，保证内部成功比例不失真。加噪后对成功数和总数进行联合计算。若某单元样本总数过少（低于安全保护阈值 $\tau$），系统会自动启动“安全抑制（SUPPRESSED）”，避免在样本不足时被噪声放大或被针对性刺探。

### 5. 当前最热门的任务是什么？（热门任务 Top-K / Top-K Tasks）
- **业务场景**：在配置的任务类型中，哪些任务的受众最广？
- **业务输出示例**：
  1. 代码生成与审查（Rank #1）
  2. 文档总结与翻译（Rank #2）
  3. 业务数据清洗（Rank #3）
- **业务意义**：排名完全建立在经过差分隐私扰动后的评分之上，杜绝外部根据精确名次推断临界任务的单人微小变动。

# 第4章：输入数据长什么样

系统不需要采集任何敏感的业务明文或代码。输入数据为标准的企业调用日志流水（CSV 或 Parquet 格式）：

| interaction_id | user_id | timestamp | provider | task | success |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `i1001` | `u001` | 2026-10-20 09:31:02 | **OpenAI** | **技术类** | 成功 (1) |
| `i1002` | `u001` | 2026-10-20 09:35:18 | **OpenAI** | **技术类** | 失败 (0) |
| `i1003` | `u002` | 2026-10-20 10:01:44 | **Kimi** | **文档类** | 成功 (1) |
| `i1004` | `u003` | 2026-10-20 10:15:30 | **DeepSeek** | **分析类** | 成功 (1) |

### 4.1 字段业务含义说明
- **`user_id`（员工标识符）**：公司内部匿名工号或混淆哈希，系统据此建立员工级聚合轨迹。
- **`timestamp`（交互时间）**：ISO 8601 标准时间，用于划分时间窗口（如最近 7 天、30 天）。
- **`provider`（大模型供应商）**：前台向业务人员展示为标准供应商名称（**OpenAI**、**Kimi**、**DeepSeek**）。系统在底层计算中采用固定不变的稳定标识符（`provider_a`、`provider_b`、`provider_c`），确保即使业务显示名称修改，历史安全审计账本也不会断裂。
- **`task`（业务任务类型）**：分类体系中的标准化任务标签（如技术类、文档类、分析类）。
- **`success`（执行状态）**：大模型调用是否成功（1 代表成功，0 代表报错/超时/被拦截）。

### 4.2 严格的数据合规红线
系统内置了 **6 项数据质量与合规性自检**。如果上传的数据中包含 `prompt`、`response`、`content`、`query_text` 等明文文本列，系统会立即触发安全拦截，坚决拒绝处理明文私密内容。

# 第5章：差分隐私到底保护什么

许多非技术人员经常会问：“我们把员工名字隐去叫 `u001`，难道还不够安全吗？”
行业痛点表明：**单纯的“去标识化”（Pseudonymization）根本挡不住交叉比对攻击。**

### 5.1 通俗场景解释
假设市场部员工“张三”在过去 7 天内深度使用了模型 300 次，尝试编写一份极其敏感的新产品商业计划。
攻击者可能已经通过其他渠道（如钉钉在线状态、出差记录）获知张三在某个时间段工作活跃。如果外部供应商拿到的统计数据能够随着“张三的数据是否参与计算”而发生微小变动，攻击者就能通过多次比对精确验证张三是否在推进该项目。

### 5.2 用户级差分隐私（User-Level DP）
差分隐私的承诺用大白话来说就是：
> **无论员工张三的全部 300 次使用记录是完整包含在数据集里，还是被彻底抽走，系统向外部发布的最终统计图表，在概率分布上都几乎没有区别。**

外部接收方即便拥有全天下所有的背景知识和超级计算机，也无法以显著高于瞎猜的概率断定张三到底有没有参与调用。

### 5.3 为什么是“用户级”而不是“记录级”？
- **记录级保护（Record-Level DP）**：假定单条日志相互独立，只保护某一次特定的按键或调用。
- **用户级保护（User-Level DP）**：系统保护的是**一个员工在整个统计周期内的完整历史轨迹**。
因为在企业场景中，真正属于个人隐私的是员工这整个人及其长期的工作习惯，而不是单独某一条毫无上下文的毫秒级日志。

# 第6章：为什么不能让一个用户无限影响统计结果

要实现严格的差分隐私，系统必须回答一个关键问题：**一个人最多能让统计结果产生多大偏差？**

### 6.1 极端用户的现实挑战
在企业真实环境中，员工使用大模型呈现严重的“长尾分布”：
- 普通员工：每天正常问答 10～20 次；
- 重度员工（如编写自动化爬虫或高频测试脚本的工程师）：每天可能自动循环调用 10,000 次。

如果不加干预，直接将这 10,000 次计入大盘，那么为了保护这位工程师的隐私，系统就必须按照“有人能凭空增加 10,000 次”的标准去加入天文数字般的随机噪声。这样一来，加噪后的数据就会彻底变成无意义的乱码，丧失任何统计分析价值。

### 6.2 贡献限制（Contribution Bounding / Clipping）
为了解决这一矛盾，系统引入了贡献限制机制：
为每位员工设定一个最大统计贡献阈值（记为 $C$）。
- 某员工原始调用次数向量为 $(30, 40)$，其综合影响大小为 $\sqrt{30^2+40^2} = 50$；
- 系统设定的上限为 $C=20$；
- 缩放因子为 $20 / 50 = 0.4$；
- 限制后该员工计入统计的贡献变为 $(12, 16)$。

```text
原始用户贡献: (30, 40)  [影响模长 = 50]
           ↓ 缩放因子 min(1, 20/50) = 0.4
受限有效贡献: (12, 16)  [影响模长严格限制在 <= 20]
```

### 6.3 贡献限制的双重作用与代价
1. **好处 1**：消除极端重度用户对全盘数据的绑架；
2. **好处 2**：确定了单人最大可能带来的变化上限（在技术上称为**全局敏感度 $\Delta_2$**），系统从而能够精准计算出需要加入的最少差分隐私噪声量；
3. **代价**：**截断本身会带来结构性偏差（Clipping Bias）**。如果 $C$ 设得过小，重度用户的实际工作量就会被大幅低估。

# 第7章：差分隐私噪声是怎么加的

完成每位员工的贡献限制后，系统汇总全员数据，并向最终结果中注入精心校准的随机高斯扰动。

### 7.1 数据的三阶段演变过程
以“技术类交互量”的统计为例：

```text
阶段一：企业真实未加噪数据 (Raw Exact)
          100,000 次
              ↓  经过单人贡献限制 (Clipping)
阶段二：贡献限制后数据 (Clipped Exact)
          98,000 次  (产生 2,000 次结构截断偏差)
              ↓  注入高斯差分隐私噪声 (DP Noise)
阶段三：对外发布数据 (DP Output)
          98,350 次  (包含 +350 次随机扰动)
```

在正文中，我们用一个最简明的核心概念公式表述：
$$
\text{最终 DP 结果} = \text{受限统计汇总} + \text{随机高斯噪声}
$$

### 7.2 噪声大小由什么决定？
噪声的标准差（$\sigma$）完全由数学定理确定，主要受三个参数制约：
1. **单人最大贡献（$C$）**：$C$ 越大，单人影响越大，必须加入的噪声越大；
2. **隐私保护强度（$\varepsilon$，Epsilon）**：$\varepsilon$ 越小代表隐私保护要求越苛刻，加入的噪声越大；$\varepsilon$ 越大代表追求更高准确性，噪声越小；
3. **破绽容忍上限（$\delta$，Delta）**：极小概率的宽松因子（通常设为 $10^{-6}$，相当于百万分之一级别）。

系统通过严格的高斯机制数学推导（Analytic Gaussian Mechanism），保证所加噪声既不多加一分（保护业务精度），也不少加一厘（捍卫数学安全）。

# 第8章：DP 之后的数据到底准不准

“加入噪声后，数据到底还能不能指导业务？”这是公司领导与业务人员最关心的核心问题。

### 8.1 彻底打破“误差全怪差分隐私”的误区
许多初次接触差分隐私的人存在一个误解：只要最终数字不准，就一定是差分隐私随机噪声太大导致的。
**事实恰恰相反。** 系统将总误差解构为两个截然不同的物理来源：

```text
                        总误差 (Total Error)
                     ┌───────────┴───────────┐
                     ▼                       ▼
            截断偏差 (Clipping Bias)    DP 噪声误差 (DP Noise Error)
               [因限制大户产生]           [因加噪保护产生]
```

### 8.2 误差两层拆解对比表示例

# 第10章：什么是隐私预算

许多业务人员会产生另一个疑问：“既然每次加了噪声都是安全的，那我每天查 100 次，是不是也可以？”
答案是：**绝对不行。**

### 10.1 为什么不能无限次查询？（均值恢复攻击）
假设某单元真实的受限交互量是：
$$100$$
如果允许外部用户无限次发起新的加噪查询，每次系统都随机生成一组独立噪声：
- 第 1 次返回：`104`
- 第 2 次返回：`97`
- 第 3 次返回：`102`
- 第 4 次返回：`98`
- 第 5 次返回：`101`
- ……
- 查询 10,000 次后取平均值：`99.999`

根据大数定律，随机高斯噪声在多次平均后会相互抵消并趋向于 0，**真实私密数值将被攻击者以极高精度彻底逆向还原**。

### 10.2 隐私预算（Privacy Budget）的本质
为了抵御这种攻击，密码学界提出了“隐私预算”机制。
系统将对外发布数据造成的潜在隐私风险视为一种**消耗性资产**：
- 每次发起一次全新的差分隐私发布，就必须从账户中扣除一定额度的预算（以 $\varepsilon$ 度量）；
- 当预算耗尽时，系统立即启动刚性熔断，坚决拒绝发起任何新的加噪计算。

# 第11章：什么叫全生命周期隐私预算

系统坚决摒弃了学术演示系统中常见的“每次关机重启就重置预算”的玩具做法，严格落地了**全生命周期隐私预算（Lifetime Privacy Budget）**体系。

```text
[ 全生命周期隐私预算上限: ε_cap = 4.0 ]
┌─────────────────────────┬───────────────────────────────┐
│  已消耗有效隐私: ε = 1.34 │      剩余安全空间: ε = 2.66     │
└─────────────────────────┴───────────────────────────────┘
  ▲ 持续累加，永久受控
```

### 11.1 终身不可磨灭原则
全生命周期预算具有四大刚性约束：
1. **重启不重置**：关闭 Web 控制台、重启物理服务器，已消耗预算永久记录在 SQLite 权威账本中；
2. **跨自然日不重置**：第二天、下个月到来，历史消耗依然存在；
3. **换指标不重新计算**：今天查了成功率，明天查交互量，所有针对同一批受保护员工的发布事件都在同一个大账本中连续累加；
4. **防篡改与不可回退**：管理员在后台管理界面中，可以将上限从 4.0 调大到 5.0，但**严禁将上限调到当前已消耗数值以下**，历史发生的发布行为永远无法在物理或逻辑上被“撤销抹除”。

# 第12章：RDP 是怎么累计的

在多批次发布时，如何计算多笔查询累加后的“总隐私消耗”？

### 12.1 传统累加与 RDP 进阶记账的类比
- **幼稚做法（传统组合定理）**：如果进行了 10 次 $\varepsilon=1.0$ 的查询，粗暴相加等于 $\varepsilon_{\text{total}} = 10.0$。这种算法极其保守，很快就会把预算“账面耗尽”，导致系统无法再做任何统计。
- **先进做法（Rényi 差分隐私，RDP 记账）**：
  好比跨国金融结算。系统先将每次基于高斯机制的查询，转换成关于不同阶数 $\alpha$ 的“标准基础货币”（RDP 损失 $\rho$）：
  $$
  \rho_{\text{total}}(\alpha) = \rho_1(\alpha) + \rho_2(\alpha) + \dots + \rho_n(\alpha)
  $$
  最后在对外展示时，系统通过严格的数学转化工具，计算出最佳换算比例，得出当前用户可见的“全生命周期等效有效 $\varepsilon$”。

通过这种科学记账，企业可以用更少的名义预算，完成更多批次的日常数据分析，大幅提升了隐私预算的使用寿命。

# 第13章：为什么相同查询不会重复消耗预算

既然重复查询会消耗预算，那么如果业务人员不小心手滑刷新了网页，或者供应商在同一周内反复下载同一份 30 天月度报表，系统难道会不断扣减预算直至瘫痪吗？
**不会。系统实现了权威的规范重放机制（Canonical Replay）。**

### 13.1 确定性缓存与零增量消耗
当业务人员发起一次发布请求时，系统会在内部提取这笔查询的全部核心语义参数（指标类型、接收方标识、时间窗口、数据集指纹、隐私参数 $\varepsilon, \delta$），并计算出唯一的“发布指纹键”（Release Key）。

```text
第一次发起查询 (新发布):
  计算参数 → 执行差分隐私加噪 → 结果写入持久化存储 → 扣除对应 RDP 预算 (有效 ε: 0 → 1.0)

第二次发起完全相同的查询 (Canonical Replay):
  系统识别指纹一致 → 直接从存储库检索第一次生成的结果 → 原样返回
  【核心保证】新增隐私消耗严格为 0！绝不重新生成第二份噪声！
```

这不仅节省了计算资源，更在数学上斩断了攻击者试图通过“反复索要同一报表以平均噪声”的攻击路径。

# 第16章：持续监控怎么工作

系统借鉴了差分隐私学术界经典的**时间二叉树算法（Binary Tree Mechanism）**，将时间轴划分为可像搭积木一样复用的“标准化时间块”。

```text
                            节点 [1, 8]  (第1~8天总和)
                           ┌─────────────┴─────────────┐
                    节点 [1, 4]                     节点 [5, 8]
                   ┌─────┴─────┐                   ┌─────┴─────┐
              节点 [1, 2]   节点 [3, 4]       节点 [5, 6]   节点 [7, 8]
             ┌───┴───┐     ┌───┴───┐         ┌───┴───┐     ┌───┴───┐
            第1天   第2天  第3天   第4天     第5天   第6天  第7天   第8天
```

### 16.1 像拼积木一样组合时间段
- 假设我们要查询“第 1 天到第 7 天的累计交互量”；
- 系统不需要从第 1 天一路加到第 7 天（累加 7 次噪声），也不需要为“1～7 天”重新生成噪声；
- 系统直接调用预先生成好的树节点：
  $$
  \text{查询 [1, 7]} = \text{节点 [1, 4]} + \text{节点 [5, 6]} + \text{节点 [7, 7]}
  $$
- 只需要组合 **3 个节点**！

无论监控时间跨度拉长到 90 天还是 180 天，任意一个时间区间的查询，最多只需要累加 $\approx \log_2(T)$ 个节点。加噪次数从几十次骤降到几次，不仅极大地节省了隐私预算，更让长周期的每日平稳监控成为现实。

# 第17章：持续监控里为什么还有每日上限和周期上限

在持续监控中，单个重度用户的累积影响变得更加复杂。

### 17.1 双层贡献限制（Two-Tier Contribution Bounding）
假设工程师李四写了一个脚本，连续 90 天每天都调用模型。如果系统只规定“单日上限不能超过 10 次”，那么 90 天下来李四一个人就能累积贡献 $90 \times 10 = 900$ 次，依然会对整个时间树的节点产生极大的主导偏差。

因此，系统在时间二叉树机制中同时引入了双重保险：
1. **单日上限（$C_{\text{day}}$，当前配置为 10）**：限制单人在任何一天内最多计入的调用次数；
2. **周期总上限（$C_{\text{epoch}}$，当前配置为 40）**：限制单人在整个 90 天监控周期内，最多计入的总调用次数。

通过这种“双保险”约束，即使某些员工长期运行脚本，整个持续监控二叉树的累积敏感度也能被严格收敛锁定在 $C_{\text{epoch}}$ 之内，彻底杜绝了时间累加带来的隐私击穿隐患。

# 第21章：当前存在的问题

坚持实事求是的技术文化，本方案客观陈述系统当前存在的工程与算法局限：

### 1. 交互总量（Interaction Volume）的截断偏差仍然偏大
目前采用固定的 $C=20$ 对单人调用模长进行硬性裁剪。在包含极重度调用员工的数据集中，截断阶段导致大盘交互量缩水约 38%。虽然这不是差分隐私噪声引起的，但确实影响了交互量统计的绝对保真度。

### 2. 热门任务分类体系（Taxonomy）目前相对有限
当前验证演示环境中的任务分类配置较少（如代码、文档、分析三类）。当分类总数本身就接近于 $K$ 时，Top-K 选择机制展示出的长尾发现价值相对有限，需要扩展到几十类以上的企业业务场景中。

### 3. 参数 $\varepsilon=1.0$ 仅作为推荐默认值
当前系统默认选取的 $\varepsilon=1.0$ 是工业界常见的折中平衡值，但它并不代表适用于公司所有部门与所有统计指标的“数学最优解”。

### 4. 持续监控（Continual Observation）目前仅支持交互量
目前已打通的二叉树持续观测拓扑仅支持交互量（Interaction Volume）这一单向可加性统计，对于成功率等比率型非线性统计，持续观测的算法适配尚未完成。

### 5. 缺乏自适应参数推荐器
系统目前依赖管理员手工在预设档位（高、中、低）中选择参数，尚未实现“根据当前数据分布与预期容忍误差，全自动计算并推荐最优截断值 $C$ 与 $\varepsilon$”。

# 第23章：这个系统的技术特点在哪里

与当前业界常见的数据脱敏方案相比，本系统的技术特点体现在五个方面：

1. **指标专属的差分隐私机制（Statistic-Specific DP Framework）**：
   摒弃了“不管三七二十一，给所有报表一律加拉普拉斯噪声”的落后粗放做法。对二值化使用率采用有限域紧确界机制，对精力分配采用单纯形重新归一化机制，对成功率采用共享等比联合高斯机制，每个统计都有严谨的数学闭环。
2. **全生命周期统一记账（Unified Lifetime Accounting）**：
   不同时间、不同业务指标的历史发布统一纳入持久化账本连续计算，打破了“换个接口就从零开始”的伪隐私风险。
3. **绑定数据接收范围的权限作用域（Recipient-Aware Privacy Scopes）**：
   深刻结合外部商业多方博弈，根据接收方的角色与合谋假定划分隐私组合边界，兼顾数据共享诉求与信息防泄密隔离。
4. **权威的规范重放保护（Canonical Replay）**：
   在架构底层实现“完全相同的查询永远只生成一次噪声并永久复用”，从工程机制上彻底封死了“多次调用求平均”的均值恢复攻击漏洞。
5. **透明可视的效用误差拆解（Empirical Utility Decomposition）**：
   不仅向安全人员提供形式化的数学安全性证明，更向业务和产品团队提供真实直观的“原始真实值 vs 受限值 vs DP值”三层透明拆解，让所有人对数据的准确度心中有数。

### 附录A：五个统计 Profile 的完整数学公式体系

#### A.1 用户使用率（User Prevalence）
- **单用户贡献转换**：
  $$b_{u,j} = \mathbf{1}[m_{u,j} > 0] \in \{0, 1\}^D$$
- **贡献限制**：
  $$\|b_u\|_0 \le \min(k, D)$$
- **敏感度界定**：
  $$\Delta_2 = \sqrt{\min(k, D)} \le \sqrt{k}$$
- **高斯机制**：
  $$\tilde S = \sum_u b_u + \mathcal{N}(0, \sigma^2 I)$$
- **后处理**：
  $$\hat S_j = \max(0, \tilde S_j), \quad \hat p_j = \operatorname{clip}\left(\frac{\hat S_j}{N_{\text{public}}}, 0, 1\right)$$

#### A.2 用户归一化占比（User-Normalized Share）
- **单用户贡献转换**：
  $$x_u = \frac{m_u}{\|m_u\|_1} \in \Delta^{D-1} \quad (\text{若 } \|m_u\|_1=0, x_u=\mathbf{0})$$
- **贡献限制**：
  $$\|x_u\|_2 \le \|x_u\|_1 \le 1.0$$
- **敏感度界定**：
  $$\Delta_2 = 1.0$$
- **高斯机制**：
  $$\tilde V = \sum_u x_u + \mathcal{N}(0, \sigma^2 I)$$
- **后处理（非负截断 + 单纯形重新归一化）**：
  $$y_j = \max(0, \tilde V_j), \quad \hat s_j = \frac{y_j}{\sum_{i=1}^D y_i} \quad \left(\text{若分母为0，平滑回退为 } \frac{1}{D}\right)$$

#### A.3 交互量（Interaction Volume）
- **单用户贡献转换（$L_2$ 裁剪）**：
  $$\bar m_u = m_u \min\left(1, \frac{C}{\|m_u\|_2}\right)$$
- **贡献限制**：
  $$\|\bar m_u\|_2 \le C$$
- **敏感度界定**：
  $$\Delta_2 = C$$
- **高斯机制**：
  $$\tilde M = \sum_u \bar m_u + \mathcal{N}(0, \sigma^2 I)$$
- **后处理**：
  $$\hat M_j = \max(0, \tilde M_j)$$

#### A.4 任务成功率（Success Rate）
- **单用户共享等比裁剪**：
  $$a_u = \min\left(1, \frac{C_{\text{rate}}}{\|n_u\|_2}\right), \quad \bar n_u = a_u n_u, \quad \bar s_u = a_u s_u$$
- **联合向量拼接与贡献限制**：
  $$w_u = \begin{bmatrix} \bar s_u \\ \bar n_u \end{bmatrix}, \quad \|w_u\|_2 \le \sqrt{2} C_{\text{rate}}$$
- **敏感度界定**：
  $$\Delta_2 \le \sqrt{2} C_{\text{rate}}$$
- **单次联合高斯机制**：
  $$\begin{bmatrix} \tilde S \\ \tilde N \end{bmatrix} = \begin{bmatrix} S \\ N \end{bmatrix} + Z, \quad Z \sim \mathcal{N}(0, \sigma^2 I_{2D})$$
- **后处理与安全阈值抑制**：
  $$\hat N_j = \max(\tilde N_j, 0), \quad \hat S_j = \operatorname{clip}(\tilde S_j, 0, \hat N_j)$$
  $$\text{若 } \hat N_j < \tau, \quad \text{返回 } \text{SUPPRESSED / null}$$
  $$\text{否则 } \hat r_j = \frac{\hat S_j}{\hat N_j}$$

#### A.5 热门任务 Top-K（Top-K Tasks）
- **单用户贡献转换**：
  $$v_{u,t} = \mathbf{1}[\text{用户 } u \text{ 使用过任务 } t] \in \{0, 1\}^{|T|}$$
- **贡献限制**：
  $$\|v_u\|_0 \le \min(k_{\text{tasks}}, |T|)$$
- **敏感度界定**：
  $$\Delta_2 = \sqrt{\min(k_{\text{tasks}}, |T|)}$$
- **高斯机制评分与排名**：
  $$\tilde c_t = \sum_u v_{u,t} + \mathcal{N}(0, \sigma^2), \quad \text{Top-K} = \operatorname{argtopk}_{t \in T}(\tilde c_t)$$

### 附录B：RDP Accounting 数学定义与 Rényi 转换

对于高斯机制，在阶数 $\alpha > 1$ 下的 Rényi 散度损失定义为：
$$
\rho(\alpha) = \frac{\alpha \Delta_2^2}{2\sigma^2}
$$
由于 Rényi 散度在独立机制下满足线性可加性，对于 $n$ 次发布事件，累计 RDP 损失为：
$$
\rho_{\text{total}}(\alpha) = \sum_{i=1}^n \frac{\alpha \Delta_{2,i}^2}{2\sigma_i^2}
$$
系统在转换为经典的 $(\varepsilon(\delta), \delta)$ 保证时，采用最优界定转化公式：
$$
\varepsilon_{\text{eff}}(\delta) = \min_{\alpha \in \mathcal{A}} \left[ \rho_{\text{total}}(\alpha) + \frac{\ln(1/\delta)}{\alpha - 1} \right]
$$
系统内置离散候选阶数集合 $\mathcal{A} = \{1.5, 2, 3, 4, 5, \dots, 64, 128, 256\}$，通过高精度数值优化求得全局紧确界。

### 附录C：Continual Binary Tree 与时间二叉树技术细节

在持续观测中，时间长度为 $T$（如 $T=90$ 天）。
1. **二叉树叶子节点**：对应每一天 $t \in [1, T]$ 的统计汇总，单日贡献受限在 $C_{\text{day}}$；
2. **非叶子节点**：递归覆盖区间 $[l, r]$，表示两子节点的向量代数和；
3. **节点查询解析**：任何区间 $[1, t]$ 可唯一分解为最多 $\lceil \log_2(t) \rceil$ 个规范二进区间（Dyadic Intervals）；
4. **整体方差界定**：相较于朴素做法将方差放大为 $O(T \sigma^2)$，二叉树机制使总方差收敛至 $O(\log^3(T) \sigma^2)$；
5. **周期级约束投影**：通过投影算法保证任意员工在所有树节点上的联合最大 $L_2$ 影响受限于 $C_{\text{epoch}}$。
